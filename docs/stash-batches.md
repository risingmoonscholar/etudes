# Independent stash operations

Each journalled folder stash or explicit selection returns a persistent `stash_id`, distinct from the result envelope's per-invocation `operation_id`. Restore exactly that operation with `stash pop --id ID`; current creation-format IDs also work as `stash pop ID`. IDs are opaque handles, not secrets or filesystem paths. Missing, malformed, unreadable or mismatched IDs never select another operation. Existing explicit `--no-journal` folder mode has no restorable ID and requires manual recovery.

Several folder batches can coexist. Each has separate hidden storage and its own encrypted journal. Selection batches keep their private root and numbered slots, so equal basenames from different parents remain separate. Pop uses the complete journal's original entry indices and preserves the existing per-entry sealed/synced write order.

`stash pop PATH` (or pop in the current directory) requires a unique live batch for that journal root. Multiple matching batches or unreadable history refuse. A folder that does not exist gives `no folder at PATH`, exit 3 and `missing_input`. `stash pop --latest` deliberately considers all stash journals on the machine; `stash pop PATH --latest` limits it to that exact journal root. Fully restored batches are excluded. Current IDs encode original creation nanoseconds internally, so restoring or rewriting a journal cannot make an older batch latest. Equal creation times refuse. Legacy IDs without this creation format retain modification-time ordering: rewriting their journal can change that order, and equal modification times refuse. Only live stashes in scope are compared (that folder's, when PATH is given). Either refusal exits 3 with `journal_times_tied`, names each tied stash and prints `stash pop --id ID` for each; `details.same_time_records` lists them. Explicit ID restore bypasses this ordering ambiguity. A pop by folder uses no order, so equal times do not block it.

New stash bases use journal header version 2, authenticating the operation ID and tool within the encrypted base before progress records are replayed. Copying another authenticated journal under an operation's filename refuses. Legacy version 1 remains readable; its filename-derived identity cannot establish this binding. A legacy stash resaved after recovery gains the new header without proving its earlier filename history. Sweep's format is unchanged.

Status reports one row per live journal, persistent IDs, deadlines, total entries and observed held destinations. Held counts use no-follow metadata and do not certify that every payload is restorable. Missing destinations do not count as restored items. A damaged progress tail is disclosed. Default machine-wide roots are withheld; raw paths require the existing `status --all --paths` terminal disclosure gate. Creation results withhold selected source locations. Explicit-selection receipts also retain the minimum holding locator for existing path-based recovery callers, while persistent IDs provide exact restoration.

Due is information, never a scheduled mutation. A deadline comes from the addressed journal's holding storage. `--if-due` only gates an explicitly requested pop: early means refusal (exit 2), due or no deadline permits restoration. A plain pop can restore early with a notice. Status never restores or rewrites a journal.

Explicit-selection receipts retain `details.holding_root` as the minimum working recovery locator for existing path-based callers, alongside `details.stash_id`. They do not list selected source names. Default status output continues to redact roots. Permission-denied and decryption refusals name the undo record that cannot be opened and why, and leave held files and journal bytes unchanged. When items are not where stash left them, pop restores none of those, says what to do if the holding folder moved or was deleted, and prints the id of another stash if one exists.
