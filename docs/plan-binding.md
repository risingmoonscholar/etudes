# Applying an observed plan

Sweep and stash can explicitly export a bounded plan and later apply those original observations. A changed tree is refused with the code `plan_stale` and a message that names the folder and says to make a new plan; replay does not scan a replacement proposal and apply it silently.

`sweep apply PATH --yes` after a preview does not apply that preview. It scans the folder again and makes a new plan, so it can move different files if the folder changed. `sweep review PATH` also scans again; it shows each group of the new plan before anything moves. To move only the plan you saw, export it and apply the export with its digest, as below. Without `--json`, a sweep plan made with `--export-plan` prints that exact command, with the real digest, for the folder and tag schemes alike. With `--json` it prints no command; the digest is in `details.binding.plan_digest`. The exported apply refuses if anything the scan observed has changed. A change the scan did not observe, such as a file deeper than `--depth`, is not checked, and that file is not in the plan.

```sh
sweep ~/Desktop --since 0 --export-plan ~/desktop.plan --json
sweep apply --plan ~/desktop.plan --plan-digest SHA256_FROM_EXPORT --yes --json

stash ~/Desktop --for 3d --export-plan ~/holding.plan --json
stash --plan ~/holding.plan --plan-digest SHA256_FROM_EXPORT --json
```

Export is a preview: it creates only the requested artifact, outside the selected tree, and moves nothing. The digest is in `details.binding.plan_digest`. Keep the digest from the original response separately from the plan file. Import requires that digest, verifies the artifact checksum, and rejects truncated, oversized, unknown-version or altered files. A missing plan file is exit 3 `missing_input`, and an unreadable one is exit 3 `permission_denied`. An empty file, a folder, another tool's plan or a mistyped digest is exit 2 `invalid_arguments`. An altered file, or a digest from another export, is exit 2 `plan_stale`. Existing export files are never overwritten. Filesystems that cannot represent mode 0600 are refused.

The private binary format is version 1, capped at 64 MiB with bounded records and 4,096-byte path/string fields. It preserves raw Unix bytes for selected member paths. The artifact contains selected paths and filesystem metadata; protect it like a directory listing. Held filenames, ancestor markers and other snapshot names are SHA256 commitments. There are no payload contents, keys or environment values. SHA256 commits the metadata, root, proposal, context and acceptance/rename choices; it does not authenticate the person who exported the file. The digest alone does not defend against someone who can edit the plan file and supply a recomputed digest. Sweep apply independently re-checks every member against the filename and filesystem eligibility rules before any change, and repeats filename classification immediately before moving or tagging each item. A member found ineligible before anything has moved is refused with a zero-entry record; one found ineligible after an earlier item moved stops the apply as `operation_incomplete`, and `sweep undo` reverses the items that moved. Stash retains its whole-unit collection policy. Decoded tag entries must have a valid name and, if present, a single Finder colour suffix from 0 through 7.

Exported-plan application checks the root's device/inode identity, each observed file's device/inode, size, type, mode and nanosecond modification/change timestamps, directory-name observations and relevant ancestor project markers. It also checks the actual CLI tool version, scheme/profile configuration and a stable capability-declaration digest excluding only the volatile contract-query operation identifier. Imported planning configuration and stash's original absolute holding deadline are frozen. Changing mapping, scan depth, grace, content-inspection or sync choices requires a new export.

Sweep may accept all exported groups or select one with `--only`. Interactive review may accept, skip or rename groups. Those decisions recompute the final plan digest from the original immutable observations. They never refresh the snapshot. If the tree changes during a prompt, the eventual mutation is refused. The public `apply_with_structured_progress(&Plan, ...)` entrypoint accepts an unbound plan and does not enforce the selection-specific checks listed below for other callers. Stash's explicit-selection command uses it after `selection::prepare` checks selected object types, symlinks, duplicate or overlapping identities, sync locations, the holding parent, and cross-volume directory constraints; it also reserves a private holding root before constructing the plan. The other apply entrypoints take a bound plan and independently supplied current context. Read-only display proposals cannot be passed through those bound entrypoints.

Direct `sweep apply PATH --yes` makes a fresh proposal and validates root identity, entry identities, permissions, layout and project markers before moving. An open writer may change an existing regular file's size and timestamps: same-device rename preserves its inode and open descriptor. Exported replay and interactive review retain strict size and timestamp checks. Ordinary `stash PATH` also retains strict metadata validation. To apply an earlier preview, use explicit export and replay; direct apply never substitutes for that replay.

A direct attempt that loses a planning race retains a sealed empty journal record when journalling is enabled. The refusal says the folder changed just now and that nothing was moved. Exported-plan refusal creates no journal or case-folding probe. A stale exported plan remains stale; the caller must explicitly make a new plan.

The snapshot observes the same depth, whole-unit policy, protected-directory exclusions, package opacity and marker probes used during planning. It binds observed metadata, not unobserved package or directory contents. Unreadable held directories are opaque: their observed directory identity and permissions remain bound, and none of their unobserved children can become selected sources. Safe sibling operations remain available. Planning adds no journal edge-hash/content reads. Changes outside that declared observation scope remain unproven. Nanosecond metadata checks can conservatively reject harmless changes; they are not cryptographic payload verification or an OS filesystem lock. Existing destination collision, overwrite refusal and crash-recovery checks still apply after binding validation.

Core fixtures and end-to-end CLI replay tests cover changed, added and replaced files, new project markers, root replacement, stale contexts, modified artifacts, original-digest enforcement, selection/rename fidelity, and unchanged replay followed by undo. Existing collision and injected journal/move failure tests retain their original assertions.

For every caller, including unbound plans, the executor keeps each accepted destination inside the plan root, within one stated limit: these checks are not an OS filesystem lock, so a checked folder that is moved as a whole after its check, or a change made by hostile code running as the same user, is not stopped. Group names cannot be absolute or contain parent (`..`) or empty components. Before filesystem mutation, it resolves the destination's existing folder or closest existing ancestor and refuses a resolution outside the root; it repeats this containment check around destination creation before each move. On macOS each move is then made into the folder that passed the checks: the folder is opened without following a link, its device and inode must match the identity recorded at planning or creation, and the rename, or the cross-volume copy, is made relative to that open folder. A folder replaced, or swapped for a link, after the check is refused with the folder-changed error instead of being followed. Undo's move back into the original source folder works the same way. On other systems the identity is checked by path just before the move, so a swap in that instant is not stopped there. This check does not restrict source locations: stash's explicit selection may collect files from several parent folders into destinations inside its holding root. Directory identity, collision and overwrite checks still apply.

Tag policy. A plan records whether tagged Finder items were included and how many the scan left alone, in a second optional trailing section written only when it says something. A plan file from before tags were honoured loads as not including tagged items; apply then re-checks every item's tag at move time and holds a tagged one. The section is covered by the digest, and an exported plan fixes its policy: `--include-tagged` cannot be passed with `--plan`.

Tag plans. `sweep --scheme tags --map EXT=TAG` writes a plan whose groups are tags: each group's name is a tag and its members are the files that get it. A third optional trailing section marks the plan as adding tags, so a plan that moves files keeps its earlier encoding and digest, and a tag group in a plan without the section (or the section on a plan with folder groups) is refused on load. The tag name, whether it was new when planned and the exact string to store are part of the digest. The profile binds the extension-to-tag map. Applying a tag plan checks the same observations as any other plan, and a file's tag change alters its ctime, so a plan made before the tags changed is stale. A tag plan is applied only from an exported plan; `sweep propose` refuses it.

Per-file proposals. `sweep propose` takes an exported plan, its digest and a proposal file, and writes a new bound plan with its own digest. It moves nothing and reads no file contents. The plan file records the real paths of files that no group claimed, in an optional trailing section covered by the digest, so the exported item list is frozen with the plan: an edited plan file fails the digest check on load, and a proposal that cites another digest is refused as stale. A proposal can name only a listed item, never a file the scan held back as personal-looking, too recent, still downloading, in a project folder or package, a link or hidden. Destination folders must already exist directly under the root and appear in the plan's observation; their device and inode are checked again at apply.
