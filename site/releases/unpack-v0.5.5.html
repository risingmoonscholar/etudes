unpack v0.5.5 — leftover cleanup and progress

A later extraction cleans up after a killed one, but only what it can prove is its own leftover.

  • A later extraction into the same destination removes a folder left by a killed extraction, and names it on stderr. It first checks the exact name, that the folder is a real directory you own, that its lock file names that very folder by device and inode, and that the lock is free. A running extraction holds the lock.
  • A symlink, a copy of a leftover, a folder from an older version and anything else unproved stay in place, and each is named with a step that works. A failed removal does not block the extraction. --json adds leftover_folders_removed and leftover_folders_kept under effects when not zero.
  • When the destination's parent folder was moved while unpack extracted, unpack failed and said "Nothing was left behind." That was false: its hidden .NAME.unpack-….partial folder, with every file extracted so far, had moved with the parent. unpack now holds that folder open, finds it where it went, checks by device and inode that it is the same folder, and removes it there. A folder that took the old name is not touched. If unpack cannot find the folder again, it names the old place and the hidden folder to look for, instead of saying nothing was left.
  • --progress-json now covers extraction and --list. Progress comes from the judged listing and the private staging folder, not from extractor output. Redirected runs of 100 or more members print milestones on stderr.
  • SECURITY.md now states that code running as you can forge the staging marker that this cleanup checks.
  • An argument that is not valid UTF-8 is refused with exit 2 and invalid_arguments. It used to panic.
  • A safe ZIP is no longer called damaged when several unpack runs work at the same time. On macOS the system unzip can fail to open unpack's private copy of the archive, which unpack gives it as a /dev/fd path, while another program opens a path with the same number. unpack now starts unzip again, up to 3 times in all, only when unzip exits 9 with its own "cannot find or open" line for that path and nothing was written. tar and gunzip still run once.
  • If all 3 attempts fail, unpack exits 3 with the new reason private_copy_unopened, retry later, and says the archive was not found to be damaged and to run the same command again. A damaged archive still gets archive_unreadable after one attempt.

JSON: the result envelope stays at schema_version: 4. The unpack capability declaration is version 9; it lists private_copy_unopened for extraction and --list.
