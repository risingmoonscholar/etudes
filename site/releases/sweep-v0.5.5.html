sweep v0.5.5 candidate — remembered routes and checked moves

Sweep can now remember a route you chose, and each move takes the file from the folder it checked and puts it into the folder it checked.

Two limits to know. sweep apply FOLDER --yes scans the folder again and moves what it finds then. It does not apply the plan you previewed, and it can move different files if the folder changed. To apply exactly what you previewed, save the plan with sweep FOLDER --export-plan FILE and run the sweep apply --plan FILE --plan-digest SHA --yes line it prints; that apply refuses if anything changed. And a file's age does not prove that no program is using it: the one-day guard (--since, default 1d) only skips files changed in the last day. Check the plan before you apply it.

  • sweep apply PATH --map EXT=Folder --save-routes --yes saves the routes to the existing-folder profile after an apply that moved every planned file. Only a route to an existing, visible folder directly inside the scanned folder is saved, and it needs an undo journal. A clash with a saved route is refused before anything moves. Your own text and comments in the profile stay. Undo moves the files back but keeps the route.
  • A refused, failed or partial apply saves nothing; details.routes_saved says why. If the save fails after the files moved, the result is incomplete with profile_write_failed, and the message prints the lines to add by hand.
  • A saved route moves any number of matching files, one or two included. If the route's folder is missing, sweep creates it, but only when the run moves at least one file into it, and the plan says so before anything moves. Undo removes that folder if it is empty after the files go back.
  • A new folder still needs 3 or more files. A built-in group's folder, such as Documents, or a --map folder that is already there takes one or two files of that kind. The plan says when files stay because sweep would have to make a new folder for them.
  • A routes profile that starts with a UTF-8 byte order mark, which some macOS editors write, is read. Saving routes keeps the mark and every other byte you wrote.
  • sweep undo of an apply that saved routes says the routes stay in the profile, names it, and says how to drop a route.
  • A scan that leaves files with no group says so and gives a step that runs as printed: a --map command to a new folder named Routed Files for you to rename, or sweep propose --help. It never names a folder or file it found. --json keeps it as details.routing_hint.
  • On macOS each move goes into the destination folder that passed the check: the folder is opened without following a link and its device and inode are checked on the open folder. A folder swapped for a link during apply is refused instead of followed. Undo's move back works the same way. A write-only folder still takes a move.
  • On macOS each move also takes the file from the source folder that was checked. The folder is opened without following a link and checked against the device and inode recorded before the first move. A source folder swapped during apply stops the run with plan_stale; files moved before the swap stay moved, and the message gives the undo step. The Finder tag check and the locked-flag check still read by path, because macOS cannot read a tag through a folder descriptor.
  • A move that failed after its copy to another disk landed no longer leaves that copy behind while saying nothing moved. The copy is removed before the message. If it cannot be removed, the message names it, says undo cannot see it, and gives the step; --json adds details.copy_left.
  • An undo record that does not open with the current key is kept past 30 days, so the right key can still undo it; sweep forget still removes it. Sweep no longer drops stash records. A scan, status or verify no longer drops records at all.
  • Folder names, extensions, schemes and durations you typed are shown as you typed them, without debug quotes and backslashes.
  • Files and folders with the locked flag are left in place and counted under skipped.locked_skipped; an item locked after the scan is counted as held_locked. Every message says how to clear the flag.
  • Finder aliases are skipped. Sweep reads only the alias flag, never resolves the alias and never reads its contents.
  • A folder held back only because its files are too recent says to retry later when those files would form a group once the window passes.
  • The steps under a plan now say what each one does. Apply: says it scans again and moves what it finds then, and Save: says it saves the plan and prints the command that moves only that plan.
  • Each apply is its own operation, so two applies of one folder need two undos. After an undo, sweep says what the next sweep undo FOLDER will reach and gives the step that does it.
  • When two undo records that undo could choose have the same time, sweep undo moves nothing, exits 3 with journal_times_tied, names each record and prints sweep undo --id ID for each one. sweep status marks tied records.
  • Two sweep apply FOLDER --yes of one folder at the same time: the one that loses before it moves a file now exits 2 with plan_stale and says "FOLDER changed just now, perhaps by another run. Nothing was moved. Scan and apply again." Before, it could exit 3 with operation_incomplete and leave a record that sweep status called damaged. Its record now reads refused planned=0 moved=0. A loser that moved at least one file still exits 3.
  • Two sweep undo of one apply at the same time no longer both move the same files back. The second says another sweep apply or sweep undo is working on these files and waits. If the first restored every file, the second says "Nothing to undo. Another sweep undo restored these files." and exits 1 with nothing_to_do. If the first stopped part way, the second restores the rest. An undo that waited never undoes an apply made after it started. This needs advisory locks on the volume that holds the undo records.
  • sweep status run while an apply is still moving files no longer calls its record interrupted or damaged. It lists the record as in_progress, says "sweep is working on this record now. These counts are what it has recorded so far.", and gives no undo step. --json gives state in_progress, damaged false and command null.
  • The steps under a plan print a folder whose name holds a tab, a newline, an escape or another control character in the $'…' form, so they work when pasted. Before, they printed <path>, which the shell read as redirects. --quiet still prints <path>, because it promises not to print names.
  • sweep status run while an apply or undo is writing the record no longer calls the record damaged. It reads again for about a second; if the record is still changing, it says the record is not damaged and to run the same command again when that apply or undo finishes. It still exits 3 with journal_unreadable.
  • When you moved files back by hand before sweep undo, undo now says "N files were already back in place; the undo record now says so." Before, it said they were home "from an interrupted restore", which may not have happened.
  • --progress-json now also covers sweep undo.
  • An argument that is not valid UTF-8 is refused with exit 2 and invalid_arguments. It used to panic.
  • On macOS each journal record is ordered behind its move with a barrier sync instead of a full drive flush. On 9,999 small files apply measured 50.3–56.7 s before and 19.4–21.3 s after.

JSON: the result envelope stays at schema_version: 4. The sweep capability declaration is version 18; it lists routing under routing, the status state in_progress, and the refusal code journal_times_tied for sweep undo.

Plans: an exported plan written by an earlier version still reads. A plan that holds a saved-route group needs 0.5.5 to read: an earlier sweep refuses it.
