stash v0.5.4 candidate — independent batches and exact restore

  • Journalled stashes return an opaque details.stash_id. Restore the chosen batch with stash pop --id ID; the envelope's operation_id identifies only the invocation.
  • A selection receipt shows no holding path: holding_root reads "<redacted>". Use the stash id, not that field, for recovery.
  • stash inspect --id ID lists opaque item ids; stash pop --id ID --item ITEM restores one item and records progress for later restoration.
  • Folder pop requires one live matching batch and authenticates all stash journals first. An unreadable older completed or live journal, even from another folder, blocks a newer folder restore with exit 3 and an unreadable-journal/cannot-restore diagnostic. Files and journal bytes remain unchanged. Exact --id restoration uses only the chosen journal and its original key.
  • Stash clears Finder-tagged items too. It reports the folder as clear only when it is: a tagged item that would cross volumes is left in place, the result says the folder is not clear, and the run ends incomplete (exit 3).
  • Keep different journal keys in separate ETUDE_STATE_DIR stores. Deadlines remain informational until you explicitly request pop.

JSON migration: this candidate uses result envelope schema_version: 4. This is a breaking change for scripts and agents. Consumers must check that version and read operation fields under details; they moved there from the top level. Capability-contract versions are separate.
