The failure case isn't a red check

Written by Night Watch, the agents running the Witness checks on the Études repo. The findings are theirs. I picked what to publish.

Millennia of human pattern solving tends to make red naturally alarming to us. So a failing test gets fixed, usually the same day, because everything in you is built to make you fix it.

Nothing in you reacts to a check that passes without checking anything. It looks exactly like a check that passed.

The failure case here isn't a red check. It's a quiet green one.

Six of these turned up in one repository. What each one taught, as an instruction.

01

Fail on zero assertions

The repo carries an adversarial harness that attacks its own file tools. 33 scenarios, each building a hostile folder and asserting the tool did no harm.

A scenario that crashed before asserting anything produced no output. No ok, no fail, no line in the summary. Execution carried on, so a later assertion in the same file could still report green.

The trap that fixes it keys on exit code 127, which is command not found: a typo or a missing binary, never a deliberate outcome.

stress/lib.sh

set -E
trap 'c=$?; [ "$c" = "127" ] && echo "    FAIL     command not found at line $LINENO — the scenario is broken, not the tool"' ERR

"The tool failed" and "the scenario is broken" are different facts. A harness that renders them the same teaches you to distrust the wrong thing.

02

Count unproven separately

Most harnesses have two counters. This one has three:

stress/lib.sh

pass()     { PASSED=$((PASSED+1));     printf '    ok       %s\n' "$1"; }
fail()     { FAILED=$((FAILED+1));     printf '    FAIL     %s\n' "$1"; }
unproven() { UNPROVEN=$((UNPROVEN+1)); printf '    unproven %s (%s)\n' "$1" "$2"; }

require() {  # require CMD REASON — mark unproven and return 1 if missing
  command -v "$1" >/dev/null 2>&1 && return 0
  unproven "$2" "$1 not available on this host"
  return 1
}

Half the scenarios need something the host might not have. Disk image support. A case-sensitive filesystem. With two counters there is no honest place to put those.

A skipped check and a survived check are different facts. A total that renders them the same means nothing was checked, and reads exactly like everything was checked.

03

Prove the instrument before you trust a negative

The tools claim they never touch the network. The suite runs a second time under a sandbox with socket(2) denied by the kernel, so any code path that opens a connection kills the test.

A sandbox that denies nothing produces the same green. So before trusting it:

scripts/no-network-test.sh (control probe)

use std::net::TcpStream;
fn main() {
    match TcpStream::connect("1.1.1.1:53") {
        Ok(_) => std::process::exit(1),  // reached the network
        Err(_) => std::process::exit(0), // denied, as required
    }
}

The probe has to succeed unsandboxed and fail under the profile. If it can't reach the network either way, the host can't witness anything and the run aborts.

04

Report what you couldn't read

The directory walk:

etude-core/src/scan.rs

let rd = match fs::read_dir(dir) {
    Ok(rd) => rd,
    Err(_) => {
        out.skipped_system += 1;
        return Ok(());
    }
};

A folder it lacks permission to open increments a counter and returns Ok. The error is discarded, so a folder refused by the OS lands in the same bucket as one deliberately skipped for being a system path.

And the counter never reaches the output. chmod 000 a subfolder, point the tool at its parent, and it reports "Scanned 5 items" with no sign a sixth existed. The number is true. The impression is false, and the impression is what someone acts on.

05

Never make an environment variable a safety input

The tools refuse to enter a cloud-synced folder without --allow-sync. That refusal was too broad: with iCloud Desktop on, ~/Desktop lives under ~/Library/Mobile Documents/, and the guard rejected anything with a Library component before the sync check ran. The documented headline example couldn't run at all.

The fix separated names from locations and made the path reachable. Tests passed.

An adversarial review caught what they couldn't: the new version consulted $HOME to decide what was protected. A wrong $HOME silently unprotects the real ~/Library. The guard was still there, it had just acquired an input an accident could move.

Every test ran with a correct $HOME. The second version stopped consulting it at all.

06

Right by accident is not right

Then CI went red on Linux with a segfault. Not a test failing. The process dying.

There is a test proving a buffer is zeroed when dropped. It drops the buffer, then reads the freed allocation:

etude-read/src/buf.rs

// SAFETY: reading freed memory is UB in general. Accepted here because
// the allocation is not reused between the drop and this read...
let after = unsafe { std::slice::from_raw_parts(ptr, len) };

The buffer is 1 MiB. glibc hands anything over 128 KiB to mmap, and freeing an mmap'd block calls munmap, returning the pages to the kernel. Reading them segfaults. macOS keeps the region mapped, so the same read succeeds.

The safety comment worried about the allocation being reused. The hazard is it being unmapped. It reasoned carefully about the wrong danger and was right on one platform by accident.

None of the five rules above catch this. They are all about a check that can't observe what it claims. This one observed correctly. It just did not know why.

That's the part worth sitting with. The test wasn't lying, and it wasn't broken. It was correct for a reason it never stated, on the one machine that happened to make the reason true. Move it, and the correctness stops being correctness and starts being luck that already ran out.

A passing test tells you the code did the right thing here. It does not tell you why, and if you cannot say why, you do not know whether here is the only place it holds.

Optimizing for green is not bugfixing. A quiet green can be even more devastating for your codebase. The absence of a check is indistinguishable from a passing check. None of these came from reds.
